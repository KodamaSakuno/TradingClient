# ADR 0005：客户端风控的两层拆分

- 状态：已接受
- 日期：2026-08-28

## 背景

客户端风控既要保护单笔下单（余额、精度、价格偏离、重复提交等），也要在持续运行的过程中监控账户级风险（敞口上限、当日亏损熔断）。两条路径的延迟要求与评估方式完全不同：单笔下单必须低延迟、确定性返回；账户级监控需要订阅行情与持仓流、异步评估，可能触发批量撤单甚至锁仓。把两者混在一起会互相拖累。

## 决策

风控拆成两层：

- **事前规则链 `IPreTradeRiskCheck`**：挂在下单链路内，任一规则不通过即拒单并返回原因。规则包括连接守卫、单笔/单日量限、价格偏离保护、重复下单防护、风控状态闸门（`ReduceOnly` 只放行减仓单，`Locked` 全拒）。
- **事中监控 `IRiskMonitor`**：独立订阅持仓与行情推送，持续评估敞口上限与当日亏损熔断，驱动状态机 `Normal → Warning → ReduceOnly → Locked`。进入 `Locked` 时触发 kill switch 撤销全部未成交单。
- **交易所侧兜底**：Gate 期货 `countdown_cancel_all` 作为死 man's switch，客户端存活时心跳续期，客户端死亡时交易所自动撤单。

## 备选方案与理由

**事前规则链挂监控评估**：把敞口/盈亏评估也塞进下单链路。否决理由：监控是持续累积的异步评估，若每次下单都重算全账户敞口与盈亏，会显著拖慢下单路径；且行情/持仓流本身就是事件驱动，更适合独立订阅。

**事中监控进下单链路**：把监控结果作为下单前置条件同步等待。否决理由：监控可能依赖行情 tick 或持仓推送，评估耗时不可控，会阻塞用户下单；监控应写状态机，事前链只读状态机的当前档位做快速判断。

**风控完全依赖客户端存活**：kill switch 只在客户端进程内执行。否决理由：客户端可能崩溃、断网、被 kill，此时依赖客户端的风控全部失效；交易所侧死 man's switch 是最后一道防线，确保"客户端死亡"本身不会变成风险事件。

## 后果

- 规则链可插拔，新增规则不改调用方；每次拦截与状态变更写审计日志。
- 状态机 `Normal / Warning / ReduceOnly / Locked` 由 `IRiskMonitor` 写、事前链读，UI 同步显著告警。
- 死 man's switch 需要在适配器层维护心跳续期逻辑，增加实现复杂度，但换来风控不随客户端生命周期失效。

## 验证方式

- 状态机迁移与状态闸门规则的单元测试（含 `ReduceOnly` 无持仓快照时 fail-closed 的用例）。
- 每次拦截与状态变更写审计日志（含规则名与原因），审计记录可回放核查。
